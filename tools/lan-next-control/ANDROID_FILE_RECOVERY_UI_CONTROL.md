# Fixed Android file recovery and cold process control

The separate `.github/lan-next-file-recovery-ui-request.json` binds fixed f83,
one companion fixture, API35 and preview code85. Requests cannot select a method,
device, host or file path. The original group UI runner and instrumentation
parser are hash-verified in a private namespace; public API26/code83 defaults and
the shared subprocess module remain unchanged.

The first actual method creates synthetic native conversation/card/document
data, exports through Coordinator.fileExport, verifies the completed file, then
closes and moves the original producer. A test-only ActivityMonitor substitutes
the OpenDocument result using the existing FileProvider. Its filter must match
the actual contract MIME type. The production Activity, code entry, review,
recreation, explicit confirmation, FileRecoveryOwner, data gate, repository and
AndroidKeystore perform the recovery. No direct prepare/confirm or manual native
inspect/apply substitutes for that flow.

After retaining the first full raw instrumentation report and strictly checking
its single executed method, the controller force-stops only the isolated next
package. A second exact method verifies a different PID, original group/daily
identity, ledger, author sequence0, four messages/reply versions/last reply,
document hash and protected native journal continuity through real Activity
startup. Explicit pause remains set; a paused Coordinator view remains null.
Metadata-only reconciliation is not represented as a native apply/frontier.

The original producer and picker copy are not recovery inputs during the second
phase. Retained offline producer bytes are still read only by the hash oracle to
check preservation. This is not physical removal of every source/package byte.

Each phase retains its own complete original stdout/stderr, exact class/method,
status sequence and parser result. No transcript is generated or concatenated.
The generic runner's report is the actual first method only; the separate
two-phase result requires both original passes. Failed/partial reports remain.
The emulator is fresh, SDK35/qemu1 and adb serial are checked, package/version85
is inspected with the existing aapt guard and runtime PackageManager. There is
no uninstall, data clear or reinstall between phases.

Only the controller evidence directory is uploaded. No recovery code, private
key, protected tree, document, export package, UI tree or screenshot is included.
Failures retain controlled phase, exception type and original stack frames,
without the original message/cause. Local verification is Python/FS/mock only;
Kotlin compilation, SDK installation and native execution belong to cloud CI.

This is a fresh synthetic file recovery proof, not DocumentsUI interaction,
physical-device acceptance, arbitrary crash/Doze survival, cloud/TLS/GB transfer
or a stale-manager repair test. Adding this profile or passing pure guards does
not constitute native success.
