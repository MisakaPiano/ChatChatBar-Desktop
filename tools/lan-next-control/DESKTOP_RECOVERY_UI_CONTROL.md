# Fixed Windows cloud recovery component proof

`desktop_recovery_ui_control.py` selects fixed source
`480fbc2e6f6c6c0ac8cf3af937ecccb18bc73507` and the single
`DesktopCloudRecoveryUiControlTest.realRecoveryPopupPreservesPreparationAndBothConnectionChoicesAcrossColdAppRoots`
method. A separate format1 request at
`.github/lan-next-desktop-recovery-ui-request.json` triggers its Windows workflow.
Adding this controller or running Python guards is not native acceptance.

The profile executes the hash-verified existing Desktop runner in a private
module namespace. Public legacy defaults stay unchanged. It reuses that runner's
exclusive source overlay, isolated appdata, original XML retention, strict single
executed method parser and source recheck. The verified direct rclone process
owner provides bounded cleanup. No second native runner is introduced.

The cloud Windows runner downloads the fixed official rclone1.76.0 x64 archive
(32193987 bytes, SHA256
`8b4fd2737ade4e70c057ef4a49deb7cffe94b0fb9d7587c189d149823f21a1dc`).
JDK17 creates a short-lived certificate valid for localhost/127.0.0.1. Only the
Desktop test JVM receives its public-cert truststore before startup. Hostname
validation and TLS1.2 remain enabled. System trust, Gradle dependency trust and
Windows certificate stores are unchanged. Private key, server credentials,
server logs, payloads and the case directory stay under runner temp and are
excluded from artifacts. Artifacts contain the original build log/XML, source
and fixture binding and public TLS hashes.

One method exercises actual Compose entry/Popup semantics with the production
DesktopAppContainer and Windows DPAPI. Two independent original groups exercise
restore-only and save-connection choices. It closes during PREPARED review,
reopens the public entry, confirms actual native card/group/root restoration,
checks protected route persistence and opens a new cold container without a sync
page. Seeding uses an explicit authenticated target upload. This does not prove
ordinary automatic cloud upload or saved-route subsequent automatic delivery.

Scope remains component/container and same-user Windows protection. It does not
cover packaged Main, physical input, Android recovery, commercial providers,
post-READY interrupted UI reentry, latest-conversation/media recovery or GB
performance. The separate real-WebDAV runtime-chat proof covers conversation
recovery in domain/file scope; evidence from the two tests is kept distinct.

Only Python/FS/mock guards may run locally. Native execution, JDK/server setup
and binary download belong exclusively to the cloud workflow. Preserve failures
and original XML even when native exit times out; timeout never counts as PASS.
