# Desktop Task Center

- `DesktopTaskCenter` observes registered owner flows; it does not schedule feature work. Row IDs are namespaced by owner, stop/retry dispatches to the original ID, and stopRequested remains active until the real owner publishes a terminal state or retires its session activity. Observer shutdown joins its own collectors/commands, separate from business shutdown.
- `DesktopTaskCenterSources` projects TaskRuntime chat/image/repair and its existing document/card-design children. `ownedWork` uses the same UUID and Job already in TaskRuntime's shutdown drain, with completion observed after that child finishes. Format-card completion means candidate work, not applying/saving an entity. Unknown repair commit remains UNCONFIRMED and is not replayable retry.
- `withCardDesign` is shared by several creative owners; only the format-card caller sets `formatCardCandidate=true`. Other children remain generic creative work with no invented format-editor target. Document preparation uses its actual usage session to distinguish chat-history indexing from a character document.
- Memory rows observe actual coordinator.runningSessions, including manual actions/reads. They are session activity, not paid-call proof. Stop uses coordinator.stopAndJoin(rowSession), never DesktopMemoryController.stop()'s selected panel session or permanent deletion cancellation. Session disappearance is not synthesized success/history.
- Fish rows observe the already-created voice coordinator's actual batch ID/session/message, phase and true counts. Streamed text, confirmations and error bodies are not copied. Stop calls that batch's existing `cancel(id)`; it is not a blanket session stop or a separate drain proof. Batch disappearance does not synthesize a completed notification. Retry/text-confirmation states remain waiting, and confirmation stays in the original voice UI.
- Full-backup export/check/restore-preparation rows use a UUID bound to the controller's original operation Job. Terminal publication occurs in its completion handler after password wiping and inspection cleanup; stale IDs cannot stop a newer operation. Picker cancellation is explicit metadata, not successful export. Cleanup uncertainty or cancellation/error with an already scheduled restart remains UNCONFIRMED, never a claim that durable restore preparation was undone. Catalog/leave cleanup are not notified. DATA targets select the matching export/check surface without starting work.
- AppContainer registers projections when each lazy owner is constructed; displaying the center must not initialize unrelated feature owners. It drains the observer after the existing business owners. Local context labels resolve only relevant session/card/document/draft names, are cached for retained rows, and remain separate from the fixed kind/status notice payload.
- Shell entry uses the existing modal/root/leave guards and native title-bar hit exclusions. A target carries actual session/card/document/draft IDs; opening a generic route does not prove target navigation. Preserve dirty editors and verify that the exact target still exists.
- Chat message targets use `revealMessage` and the repository's bounded page/viewport anchor, retaining the composer. Character document focus validates both current draft and persisted card, then expands/scrolls without reloading the same dirty editor. Format candidate navigation only reveals its still-pinned draft; it never creates/replaces a draft. Manage target requests wait for existing transfer owners to become idle and then use the normal section leave guards. Local rows retain a short task ID even when names match.
- When leaving a busy Manage route for another task target, keep the center open with an explicit busy message. A same-route Manage request is retained until its original owners become idle. User-cancelled dirty-editor leave remains cancelled, without automatic later navigation.
- Feature-specific verification starts with DesktopTaskCenterTest, actual owner cancellation/drain and DesktopTaskCenterPanelTest (narrow/wide synthetic captures via CCB_TASK_CENTER_REVIEW_DIR). Message paging tests need more than ChatRepository.MAX_WINDOW_TURNS real User/Assistant groups: consecutive assistant messages are intentionally one group. Await the original async stop callback within its existing budget, not only the synchronous stopRequested projection. Runtime, UI, tray capability, OS notification delivery and human acceptance are separate evidence; current scope is tracked in docs/desktop/251_TASK_CENTER_AND_TRAY.md.
- `DesktopTrayController` owns one AWT backend, explicit hide/show/tasks/exit actions and settings-backed `taskNotifications`. Main keeps the same Window composition with `visible=false`; ordinary X still uses the original close/guard/drain. Unsupported/failed attachment cannot hide the window. Notification payload is only fixed kind/status; successful displayMessage submission is not proof of OS delivery. AppContainer detaches the tray after feature drains and before closing the task observer. Headless tests inject a backend and do not initialize SystemTray.
