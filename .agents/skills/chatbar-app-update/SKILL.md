# ChatBar App Update

`test_proxy_cli.py` complements first-byte tests: the actual prepared helper CLI consumes application route JSON, discovers synthetic authenticated metadata over locally trusted HTTPS/HTTP CONNECT, follows the original permitted CDN redirect over SOCKS5, downloads a never-executed fixture, and independently re-verifies it. Its process-local synthetic CA does not disable certificate/hostname validation or modify the OS store. Set `CCB_UPDATE_PROXY_JAVA_CLASSPATH` to cloud-compiled `fixtures/UpdateCommandBridge.java` to cover the Windows JDK ProcessBuilder/CRT boundary; Python subprocess alone does not cover it. `test_proxy_arguments.py` checks bounded decoding and actual CLI refusals before cache/network access. These are separate from real GitHub discovery/user acceptance and from `test_client.py`, whose policy fixtures import repository modules.

`DesktopUpdateNetworkRouting.signedRoutesArgument` transports the noncredential UTF-8 JSON as bounded canonical Base64 via `--proxy-routes-base64`: raw compact JSON loses double quotes through Windows JDK ProcessBuilder. The helper retains mutually exclusive legacy `--proxy-routes` for direct callers; malformed/oversized encoded routes refuse before cache/network rather than falling back to DIRECT. Route selection and validation remain shared with the existing typed transport.

The opt-in cloud-only `:desktopApp:verifyUpdateRuntimeArgv` executes actual `DesktopUpdateRuntime` discovery/download and the same production `helperArguments` revalidation through Windows ProcessBuilder. It requires `CCB_ARGV_FIX_BASE` with a fresh prepared runtime and a reports directory, uses a synthetic installed1233 identity and the fixed public1245/sign27 target, and never executes an installer. Its live-network proof is separate from local synthetic CONNECT/SOCKS tests and human update acceptance.

Desktop manual release checks use `DesktopUpdateChecker`; installed startup discovery/download/reverification use the separate `DesktopUpdateRuntime` Python TUF helper. Both capture the currently saved application proxy policy for each new operation. `DesktopUpdateNetworkRouting` uses the shared selector and explicit selected-route socket factory; its four permitted HTTPS host routes preserve HTTP/SOCKS/DIRECT types; their noncredential JSON uses the encoded argv protocol described above. `GitHubFetcher` selects urllib3 HTTP CONNECT/PySocks managers per typed destination without changing the existing URL/signature/redirect/attempt controls. PySocks is included in the updater's hash-locked wheels. The physical routing regression covers the checker/default constructor and hot next-request changes in fresh JVMs; its opt-in packaged run verifies actual app-image class origins. `test_proxy_transport.py` verifies real helper CONNECT/SOCKS/TLS first bytes from the prepared runtime, separately from TUF policy tests.

## Invariants

- Keep normal update flow inside ChatBar: select stable Release APK, download it, then open system installer. Open Release page only when no usable APK exists.
- Prefer `browser_download_url` from GitHub asset metadata. Keep deterministic fallback name aligned with workflow output `ChatBar-<version>.apk`.
- Fetch release metadata from GitHub Releases API first. If `api.github.com` is unavailable, use `github.com/<owner>/<repo>/releases.atom` so update notes remain available; use the web redirect only as last-resort tag discovery.
- Treat Release body, API response, Atom feed, `AppUpdateInfo.releaseNotes`, and dialog rendering as separate gates. Success at one layer does not prove the next layer works.
- The web redirect reveals only the tag and URL; it is never a valid update-note source.
- Store packages under app-private `files/updates/`; expose only that directory through existing FileProvider.
- Before install, reject incomplete files, invalid APKs, foreign package names, mismatched version names, and non-increasing `versionCode`.
- Keep one active download. Scope UI state to asset URL so stale state cannot control another release.
- Treat unknown-source approval and installer confirmation as required Android user actions. Never uninstall, clear data, or bypass signature checks.
- Preserve failure detail in dialog. Do not silently redirect to browser after download or validation failure.
- Manual check runs application and Danbooru catalog discovery independently. One failure must not suppress the other result. Startup remains application-only.
- In Compose callers, read the collected download state when deriving `stateFor` (for example, as a `remember` key alongside update info). Collecting an unread delegated state does not subscribe rendering to progress, failures, or completion.
- Catalog updates download the complete upstream SQLite file, verify expected size, Git blob SHA, SQLite header, `quick_check`, required columns, row count, and supported categories, then prepare the matching `RankedTagIndex` before atomically replacing the app-private catalog. Completion observes the new source version, cancels stale queries, and retains SQLite references for active source readers and safely releases retired index readers. Any validation/preparation/install failure keeps the last-known-good catalog.
- When both updates exist, `全部更新` starts independent downloads concurrently. Catalog applies automatically after validation; APK installation always remains a separate user/system-confirmed action.

## Change Workflow

1. Read all entry points above before changing contracts.
2. Keep `AppUpdateInfo`, serialized GitHub models, downloader state, and both dialog callers synchronized.
3. When changing asset naming or release metadata, update checker fallback, release workflow, and tests together.
4. For missing notes, verify the exact tag with `python .agents/skills/chatbar-release-publish/scripts/verify_release.py`, then trace API → Atom → model → dialog. Do not “fix” only the Release body when the installed client is using a body-less fallback.
5. When changing download storage, update FileProvider paths and verify URI grants remain narrow.
6. Represent idle, downloading, ready, failed, permission-required, and installer-launch behavior explicitly.
7. Test API failure explicitly and prove Atom parsing supplies a non-empty body; also test prerelease exclusion.
8. Verify with update unit tests, debug Kotlin compile, and `ci.ps1 -SkipAssemble`.
9. If a release-signed device is connected, use data-preserving release deployment. Debug signing cannot validate production self-update compatibility.

## Diagnosis Rules

- If GitHub body is empty, repair published metadata first.
- If GitHub body is present but Atom is empty, release publication is incomplete for fallback clients.
- If API and Atom contain notes but app shows empty text, inspect installed-version code and runtime logs; do not claim server-side repair solved it.
- An installed APK cannot gain new retrieval logic remotely. Say which new app version must be published and installed before the fix can work.

## Publishing

Use `.github/workflows/release.yml` through `workflow_dispatch` after all intended commits reach its target branch. Supply:

- `versionName`: next unused version without relying on local build overrides.
- `releaseNotes`: short user-facing changes since previous Release; exclude implementation details.

Workflow increments Android `versionCode`, commits version metadata, tags `v<version>`, builds signed APK, and creates GitHub Release. Require the release-publish verification script to pass before reporting completion.

## Desktop Preview discovery (D-041)

`DesktopUpdateRuntime.cleanCache` shares the same completed-payload policy as automatic post-install cleanup. The NSIS success tail launches `update-handoff --complete`; its acknowledgment follows capture of the exact installer process, and it waits on that captured process without a completion-page dwell timeout, then requires zero-code exit before checking activated current pointer, manifest receipt and target config. Only then does it write a small immutable confirmation and invoke the installed Python helper. This works with older application updater handoffs because the new installer owns the tail. Failed/unconfirmed installs publish no completion authority. Python `confirmed_installation` rechecks that confirmation against the actual package/root/current/manifest. Without it all payloads remain; with it current/older builds are eligible, while future/pending selection, mismatched same-build source and busy/unknown/changed files remain. There is no two-recent retention. The original client lock and exclusive-handle/hash/final-path deletion remain; all VERIFIED/TUF/confirmation records survive. Program directories, data and rollback counters are outside this owner. Native `test_handoff.py` observes actual synthetic-process acknowledgment/exit and confirmation refusal; signed-download `test_client.py` checks real leases and retained small evidence. Exact ordinary installer lifecycle verification remains separate.

`UpdateSpaceRequired` retains the existing `3*target.length+64MiB` admission and reports actual cache path/required/free numbers. Kotlin accepts those details only for its expected absolute cache and bounded numeric fields. The pane gives the exact location, shortage and explicit cleanup action. Download/cache/install tasks project their original runtime Jobs into the task center. Cancellation checks before starting the helper and drains that exact process afterward; no confirmed helper exit yields UNCONFIRMED, not install or cleanup success.

Desktop manual Data → version/update checks call `checkDesktopProgramAndCatalog`: app discovery retains `DesktopUpdateNotices` and the signed installer owner, while `DesktopCatalogUpdates` independently checks the auxiliary catalog. Startup still checks only the application. Catalog download/apply is explicit and uses the existing verified immutable DB/index/pointer installer, never NAI credentials or the image-work lane. Studio settings render the same `DesktopCatalogUpdatePanel` and application owner; both surfaces show local status/error/retry/stop. A failed catalog check or owner preparation cannot suppress app discovery. Catalog publication-attempt evidence keeps late cancellation/failure UNCONFIRMED, distinct from prepublication cancellation.

`tools/desktop/update/validate_signed_candidate.py` validates privately prepared public role bytes in cloud against an exact reused installer, with the frozen public1233 updater and its unchanged transport. It checks increasing cached revisions, discovery, final notes text, complete download and second verification without running an installer. Its metadata fetcher is local to that cloud job, not public-network discovery. Expected notes hashes bind the LF text consumed by the signer; Windows on-disk CRLF bytes are a different digest.

Desktop stable transition uses `tools/desktop/update/version_identity.py`: actual SemVer/channel, monotonic build and legacy-root-safe storage are separate. New NSIS manifests carry `buildNumber/channel/storageVersion`; absent fields are allowed only for the exact old0.1.0-preview.N contract. `Launcher.cs` binds storage/source/manifest/READY, sealed per-version identities support damaged-stable repair, and exact same-input stage retries may complete their interrupted identity seal. New target checks retain both semantic and build order. Preview's original metadata cache remains separate from `metadata-stable`; selected-version channel routing does not bypass TUF verification. Gradle/candidate accept an explicit build number. See267 for bridge limits and separate native/real-package proof scope; current source alone is not stable runtime acceptance.

The shared release-label grammar is the existing Kotlin/transport subset (80 total characters, nine-digit core parts, 20-character prerelease identifiers, numeric prerelease bounded by Int64; no `+metadata`).
