# Sync object store

- Shared owner: `app/sharedCore/src/main/kotlin/com/example/chatbar/domain/syncStore/`. `CiphertextStore` accepts ciphertext only; `FileCiphertextStore` uses opaque random object/operation IDs, streamed length/SHA-256, immutable intent receipts, JVM plus OS admission and forced atomic publication. Listing is keyset discovery with periodic rescans, not a complete history checkpoint; no CAS, multi-object transaction or byte-resume capability is implied.
- `SyncStreamingCipher` pins Tink1.23.0 AES256_GCM_HKDF_1MB, matching the existing Desktop backup dependency. SharedCore uses compileOnly plus a JVM test dependency; Desktop supplies `tink`, Android supplies `tink-android`. Avoid packaging both platform artifacts into Android. The encryption context authenticates format/domain, opaque group/epoch, object kind and random object ID; it contains no plaintext titles, paths or content hashes.
- The cipher returns invocation-owned private prepared files only after complete encryption/decryption and file force. Decryption reads through authenticated EOF before returning a plaintext path; tail failure cleans only that preparation. Neither operation closes its borrowed input. Completed file handles own exact filesystem identities and refuse cleanup after replacement.
- `SyncEncryptedOutbox` takes an already-created private local directory, separate from source files and remote storage. Its forced immutable binary source/context binding precedes encryption; `ciphertext.bin` and `ready.bin` precede upload. A retained ciphertext without a ready record is fully AEAD/digest verified before completing that record. Reopen and upload need no original source; lost backend replies/local receipts retry the exact ciphertext and operation. A changed source/object/key or damaged ciphertext/receipt refuses. Only exact invocation staging names under a locked operation directory are reclaimable; unknown files retain evidence and refuse initial authority. Queue admission uses a canonical-root JVM lock plus OS file lock and rejects callback reentry. Receipt completion is not a cloud freshness proof, and no ordinary queue retirement exists yet.
- `protectedKeyset/open` hand the small group/epoch-bound key envelope to an injected platform protection owner. They never persist a cleartext keyset. The tests' reversible callback is synthetic boundary coverage, not DPAPI/Keystore evidence or cross-device key enrollment. A symmetric group key alone supplies no author identity, device revocation, branch ancestry or rollback protection; those require the later authenticated ledger.
- `SyncStreamingCipherTest` executes actual multi-segment AEAD through `FileCiphertextStore`, protected-key reopen, randomized ciphertext, context/key substitution refusal, tamper/truncation/trailing-byte failure, no escaped partial plaintext, empty input and borrowed-stream ownership. `SyncEncryptedOutboxTest` covers lost actual publication responses/receipts, exact-byte crash recovery, source deletion, changed bindings, damage, concurrent owners and reentry. `FileCiphertextStoreTest` remains storage-only. The engineering workflow selects the whole `domain.syncStore.*` package and uploads reports only. Shared custody below remains separate from native enrollment/runtime and UI integration.
- Primary API guidance: [Tink Streaming AEAD](https://developers.google.com/tink/streaming-aead), [Java/Android setup](https://developers.google.com/tink/setup/java). This offline owner does not access cloud accounts, provider credentials or remote folders.

- `SyncCausalHistory` is a separate in-memory content-DAG kernel, not yet Runtime authority. Each parent carries both a random version ID and canonical body SHA-256; author sequence/predecessor and per-unit previous frontiers must agree with actual ancestry. Canonical hashing streams sorted metadata into SHA-256 without a complete canonical string. Deletions retain prior version references and never derive authority from a missing record, pair baseline or clock. A stale branch changing another unit does not resurrect an ancestor; concurrent same-unit deletion/edit retains both facts until a new revision acknowledges them. Missing parents wait while independent valid branches advance; bound-parent, predecessor and unit-evidence failures have explicit states/codes. Admitted collections are frozen and same-ID different-body attempts never overwrite them.
- `SyncVersionAdmission` is mandatory and has no permissive default. It must verify the real pinned group/device ledger, signature and current revocation fence; history must be rebuilt when that policy changes. `snapshot()` copies the exact retained/admitted/rejected fact view for frozen review while discovery continues. `authorForks` exposes sequence equivocation; no automatic winner is selected. Disk indexes and native activation remain incomplete.
- `SyncCausalHistoryTest` signs actual P-256/SHA256withECDSA content using four synthetic identities, but its membership reference and content-object descriptors are placeholders: these tests prove causal/signature-kernel behavior only, not enrollment, ciphertext publication or multi-device app acceptance. They cover out-of-order/repeated delivery, stale branches, explicit deletion/edit resolution, signature/parent substitution, bad tombstones/predecessors, immutable evidence and visible same-device forks.
- `SyncDeviceLedger` pins an externally admitted group/genesis/owner certificate and last-known checkpoint, verifies the owner's domain-separated ledger signatures and exact bound parent sequence, and retains every member including permanent revocations. Revocation requires a never-reused new opaque key epoch; accepted history fences survive later rotations. Missing parents wait, invalid children keep explicit failure states, and multiple valid ledger heads refuse automatic trust selection. `current` requires the pinned checkpoint in its ancestry so an older backend view cannot replace already observed trust. Native custody must persist/enroll that checkpoint; this kernel does not discover an unseen update on a withholding backend. The present kernel has no owner transfer or ledger-fork resolution workflow.
- `SyncDeviceSignatures` verifies exact P-256/SHA256withECDSA self-signed device certificates and bounded digest signatures. `LanSyncTlsIdentity.signSyncGroupPayload` reuses the existing protected device owner and accepts only VERSION/DEVICE-LEDGER/KEY-DELIVERY digest domains. Historical verification does not discard signatures merely because a certificate date expired; live enrollment still belongs to the existing pinned TLS owner.
- Each admission view takes only complete AEAD-derived `SyncAuthenticatedGroupObject` witnesses, keyed by the exact version reference. Active offline authors can re-encrypt the same signed logical version under the latest epoch without changing author counters/parents; a new random ciphertext container/operation carries it. A revoked author's unfenced late version still refuses even if another active device rewraps it. Earlier accepted versions remain valid only through exact body-bound fence ancestry. Missing fence bodies refuse authorization until fetched. This kernel does not itself distribute keys or publish native content.
- `SyncGroupObjectCodec` writes deterministic sorted typed version/ledger metadata into an owned private preparation before the existing outbox. It reuses `LanSyncMetadataBudget/LanSyncJsonFiles`, with no attachment/total cap implied. Decoded opaque IDs/reference hashes and bounded machine fields retain constructor validation. A logical signed version ID is distinct from its random ciphertext container ID; retry retains one container, while re-encryption uses a new container/operation and preserves the signed logical version. The caller still owns durable custody of the exact signed envelope before first enqueue.
