# Sync object store

- Shared owner: `app/sharedCore/src/main/kotlin/com/example/chatbar/domain/syncStore/`. `CiphertextStore` accepts ciphertext only; `FileCiphertextStore` uses opaque random object/operation IDs, streamed length/SHA-256, immutable intent receipts, JVM plus OS admission and forced atomic publication. Listing is keyset discovery with periodic rescans, not a complete history checkpoint; no CAS, multi-object transaction or byte-resume capability is implied.
- `SyncStreamingCipher` pins Tink1.23.0 AES256_GCM_HKDF_1MB, matching the existing Desktop backup dependency. SharedCore uses compileOnly plus a JVM test dependency; Desktop supplies `tink`, Android supplies `tink-android`. Avoid packaging both platform artifacts into Android. The encryption context authenticates format/domain, opaque group/epoch, object kind and random object ID; it contains no plaintext titles, paths or content hashes.
- The cipher returns invocation-owned private prepared files only after complete encryption/decryption and file force. Decryption reads through authenticated EOF before returning a plaintext path; tail failure cleans only that preparation. Neither operation closes its borrowed input. Completed file handles own exact filesystem identities and refuse cleanup after replacement.
- `SyncEncryptedOutbox` takes an already-created private local directory, separate from source files and remote storage. Its forced immutable binary source/context binding precedes encryption; `ciphertext.bin` and `ready.bin` precede upload. A retained ciphertext without a ready record is fully AEAD/digest verified before completing that record. Reopen and upload need no original source; lost backend replies/local receipts retry the exact ciphertext and operation. A changed source/object/key or damaged ciphertext/receipt refuses. Only exact invocation staging names under a locked operation directory are reclaimable; unknown files retain evidence and refuse initial authority. Queue admission uses a canonical-root JVM lock plus OS file lock and rejects callback reentry. Receipt completion is not a cloud freshness proof, and no ordinary queue retirement exists yet.
- `protectedKeyset/open` hand the small group/epoch-bound key envelope to an injected platform protection owner. They never persist a cleartext keyset. The tests' reversible callback is synthetic boundary coverage, not DPAPI/Keystore evidence or cross-device key enrollment. A symmetric group key alone supplies no author identity, device revocation, branch ancestry or rollback protection; those require the later authenticated ledger.
- `SyncStreamingCipherTest` executes actual multi-segment AEAD through `FileCiphertextStore`, protected-key reopen, randomized ciphertext, context/key substitution refusal, tamper/truncation/trailing-byte failure, no escaped partial plaintext, empty input and borrowed-stream ownership. `SyncEncryptedOutboxTest` covers lost actual publication responses/receipts, exact-byte crash recovery, source deletion, changed bindings, damage, concurrent owners and reentry. `FileCiphertextStoreTest` remains storage-only. The engineering workflow selects the whole `domain.syncStore.*` package and uploads reports only. Version dependency scheduling, durable device-ledger storage and application UI integration remain incomplete.
- Primary API guidance: [Tink Streaming AEAD](https://developers.google.com/tink/streaming-aead), [Java/Android setup](https://developers.google.com/tink/setup/java). This offline owner does not access cloud accounts, provider credentials or remote folders.

- `SyncCausalHistory` is a separate in-memory content-DAG kernel, not yet Runtime authority. Each parent carries both a random version ID and canonical body SHA-256; author sequence/predecessor and per-unit previous frontiers must agree with actual ancestry. Canonical hashing streams sorted metadata into SHA-256 without a complete canonical string. Deletions retain prior version references and never derive authority from a missing record, pair baseline or clock. A stale branch changing another unit does not resurrect an ancestor; concurrent same-unit deletion/edit retains both facts until a new revision acknowledges them. Missing parents wait while independent valid branches advance; bound-parent, predecessor and unit-evidence failures have explicit states/codes. Admitted collections are frozen and same-ID different-body attempts never overwrite them.
- `SyncVersionAdmission` is mandatory and has no permissive default. It must verify the real pinned group/device ledger, signature and current revocation fence; the history uses one immutable policy view and must be rebuilt from retained evidence when that view changes. `authorForks` exposes sequence equivocation for the future admission/materialization owner; no automatic winner is selected. Native enrollment/key distribution, signed-ledger persistence, resource-dependency admission, disk indexes and native activation are still incomplete.
- `SyncCausalHistoryTest` signs actual P-256/SHA256withECDSA content using four synthetic identities, but its membership reference and content-object descriptors are placeholders: these tests prove causal/signature-kernel behavior only, not enrollment, ciphertext publication or multi-device app acceptance. They cover out-of-order/repeated delivery, stale branches, explicit deletion/edit resolution, signature/parent substitution, bad tombstones/predecessors, immutable evidence and visible same-device forks.
- `SyncDeviceLedger` pins an externally admitted group/genesis/owner certificate and last-known checkpoint, verifies the owner's domain-separated ledger signatures and exact bound parent sequence, and retains every member including permanent revocations. Revocation requires a never-reused new opaque key epoch; accepted history fences survive later rotations. Missing parents wait, invalid children keep explicit failure states, and multiple valid ledger heads refuse automatic trust selection. `current` requires the pinned checkpoint in its ancestry so an older backend view cannot replace already observed trust. Native custody must persist/enroll that checkpoint; this kernel does not discover an unseen update on a withholding backend. The present kernel has no owner transfer or ledger-fork resolution workflow.
- `SyncDeviceSignatures` verifies exact P-256/SHA256withECDSA self-signed device certificates and bounded digest signatures. `LanSyncTlsIdentity.signSyncGroupPayload` reuses the existing protected device owner and accepts only VERSION/DEVICE-LEDGER digest domains. Historical verification does not discard signatures merely because a certificate date expired; live enrollment still belongs to the existing pinned TLS owner.
- Each admission view takes only complete AEAD-derived `SyncAuthenticatedGroupObject` witnesses, keyed by the exact version reference. Active offline authors can re-encrypt the same signed logical version under the latest epoch without changing author counters/parents; a new random ciphertext container/operation carries it. A revoked author's unfenced late version still refuses even if another active device rewraps it. Earlier accepted versions remain valid only through exact body-bound fence ancestry. Missing fence bodies refuse authorization until fetched. This kernel does not itself distribute keys or publish native content.
- `SyncGroupObjectCodec` writes deterministic sorted typed version/ledger metadata into an owned private preparation before the existing outbox. Reads force the downloaded ciphertext, consume complete AEAD EOF, check strict UTF-8/decode working cost before typed allocation, bind group/object context and optional exact version reference, then freeze collections before creating an epoch witness. It reuses `LanSyncMetadataBudget/LanSyncJsonFiles`, with no attachment/total cap implied. Decoded opaque IDs/reference hashes and bounded machine fields retain constructor validation. A logical signed version ID is distinct from its random ciphertext container ID; retry retains one container, while re-encryption uses a new container/operation and preserves the signed logical version. The caller still owns durable custody of the exact signed envelope before first enqueue.
- `SyncDeviceLedgerTest` now obtains epoch evidence through actual codec/outbox/FileCiphertextStore/AEAD reads using synthetic existing TLS identities. It covers enrollment, reopen, revocation/backdating refusal, active offline re-encryption policy, key/fence retention, forged owner/genesis/content, visible ledger forks and last-known checkpoint refusal. Group keys are supplied by the fixture, not native enrollment/key transfer. `SyncGroupObjectCodecTest` separately covers the full signed metadata pipeline, no plaintext marker in backend files, immutable witnesses, bound references/context, budget refusal, ciphertext tamper, malformed authenticated JSON/UTF-8 and decoded identifier validation. These are controlled JVM proofs, not multi-device app acceptance.
- The unpublished typed group envelope is now format2 and the logical version canonical domain is `CCB-SYNC-VERSION/2`; format1 refuses rather than being reinterpreted. `SyncVersionContent` aliases the signed plaintext length/SHA-256 identity. Ciphertext object IDs/descriptors/epochs live in the AEAD-authenticated envelope's detached `blobs` map. Re-encrypting a unit or attachment therefore changes only its location binding/container, preserving the signed logical version, author sequence and parent references. No deployed group-format migration is claimed; legacy LAN protocol7 is separate.
- `SyncGroupBlobStore` binds source plaintext identity inside `Outbox.prepare` before encryption and again through the encryption stream's digest, then returns an epoch/object/descriptor locator. Reads force the ciphertext download, authenticate complete AEAD EOF, and match the actual decrypted plaintext length/hash to its signed/manifest identity before returning an owned file. A missing object, wrong group/epoch/plaintext mapping or wrong decrypted content never produces ready data. The caller still must validate the native unit graph/resources and admit every dependency before publishing; metadata authentication alone is not native readiness.
- `SyncGroupBlobStoreTest` uses fully written2MiB+ bytes, the real offline queues/backend/AEAD and signed metadata to re-encrypt an unsent unit plus its version under a newer group epoch. The original signed logical version/counter stays unchanged, old queued ciphertext remains local, and new content round-trips by full hash/bytes. It separately covers missing blobs and substituted plaintext identities. It does not exercise a native conversation package or production key distribution.
- Native unit/dependency inspection is in `domain.lanSync/LanSyncGroupUnitCodec.kt`. Its synthetic JVM tests take actual CharacterCard/ChatSession records through the existing Workspace capture, group unit serialization, encrypted blob queue/backend, complete decrypt/manifest checks, Workspace application and fresh target reopen with exact image/business hashes. Missing resource declarations, foreign model fields, wrong slot/hash and metadata working-budget failure refuse. This is shared repository behavior, not Desktop/Android process, device-key delivery or native-group acceptance. `LanSyncGroupPublicationQueue` enforces these inspected dependencies before sending version metadata; reducers still need the existing independent-custody/default-review policy.
- Signed device-ledger canonical domain2 also fixes the actual group-key commitment, not just an opaque epoch label. `SyncStreamingCipher.keyCommitment` hashes the domain/group/epoch-bound serialized random Tink keyset and clears its temporary bytes. Same-epoch ledger children cannot replace it. Complete decoded/prepared witnesses carry the actual cipher commitment; current-version admission requires it to match the signed current ledger. A freshly generated wrong secret with the same group/epoch labels has no current authority. Historical fenced signatures remain separate. Native key enrollment/custody must verify this commitment before accepting a supplied key.
- `SyncGroupObjectCodec.enqueue` returns `SyncPreparedGroupObject`: the normalized frozen envelope, exact outbox entry and a local witness after full retained-ciphertext verification. `SyncOutboxEntry.plaintext` binds a prepared locator to its actual decrypted source identity. `bindDeliveryHash/deliveryHash` retain an immutable local delivery-plan seal in the metadata operation directory, separate from its uploaded receipt and never sent remotely. Neither the prepared object nor that seal is a completion receipt or native data activation.
- CI always runs the selected shared/Android and Windows checks. The existing LAN large-resource job reruns for transport/other source/workflow changes or an unavailable diff base; only isolated `syncStore`/`LanSyncGroup*` code/tests and their two skill maps reuse the previous unchanged-transport proof. Its classifier emits that scope explicitly. New group-resource large proof remains a separate requirement before native group delivery; a skipped legacy job is not a new large-data execution result.
- `LanSyncGroupPublicationQueueTest` exercises actual inspected native units, encrypted offline objects and the file backend: resources before metadata, lost resource replies, source deletion after complete preparation, fresh queue reopen, repeated completion, missing/substituted dependencies, key changes before metadata, local revocation, changed plans and damaged completion receipts. These tests establish delivery ordering only; no group proposal approval or app activation is inferred.
