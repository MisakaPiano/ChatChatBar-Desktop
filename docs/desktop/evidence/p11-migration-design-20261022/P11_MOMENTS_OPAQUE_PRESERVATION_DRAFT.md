# P11 Moments 无损封存合同草案

**DRAFT / NOT IMPLEMENTED / 待独立设计审查**，2026-10-22 JST。控制点 Desktop `8c378e8cf487f6dbcb0df3f3a6f1408028185091`；官方来源 1.4.5 `1198a13cf3008de1358b8a69aa5e40b64797c8d9`。正式 baseline 仍为 1.4.1 `5e76a9cb841736bbbf3499a2e35e5789af4c5ca8`。

当前行为不变：`moment_posts` / `moment_tasks` 触发整包安全拒绝。这里的“应”“必须”均为拟议合同，不是当前实现或实施授权。

## 1. 源码事实与设计结论

精确依据见 [SOURCE_AUDIT](SOURCE_AUDIT.md) O01–O12、D01–D05、D10–D13。

- O02/O03：Post、Task 分别保存；Task 的 `postId` 可空，状态有 PENDING/RUNNING/COMPLETED/SKIPPED/FAILED。没有可直接拿来当封存格式版本的 Moments `schemaVersion` 字段。
- O02/O04：Post 拥有 card/session/sender 标识及 sender 快照；资源至少包括 `senderAvatar`、`imagePath`、`generatedImageMetadata.imagePath`。其余生成参数、失败原因和 checkpoint 仍是必须保留的原字段。
- O08：删除角色保留历史 post，并用 post 的 `senderAvatar`/`imagePath` 保护相关文件，删除该角色的 pending tasks；session 删除另有图片/录音清理。不能推导出现有删除器已保护新封存目录或 metadata 中全部引用。
- O05–O09：官方字段感知路径转换不等于全文替换；`metadata`/`extensions` 下的字段有特殊排除，未知字段不会自动获得完整资源语义。官方实体 validator 使用 `ignoreUnknownKeys=true`，能解码不等于未来字段可往返保全。

**结论：对固定已审计格式，独立封存与资源托管在技术上有条件可行；任意未来 schema 的完整资源可迁移性无法仅靠保留 JSON 保证。** 当前不能认定“无损封存已实现”或完整 `.cbbackup` 已兼容。

## 2. 三类对象必须分开

| 对象 | 保证与用途 | 禁止行为 |
|---|---|---|
| 原始来源档案 | 用户选定 `.cbbackup` 原始完整字节、长度、SHA-256；原文件不变，受控保留副本经确认后另存 | 不能把它作为已经恢复成功的替代证明；不能自动装入普通可分享备份，尤其可能含凭据 |
| 经验证封存副本 | 原始归档内记录字节与资源字节、独立清单、关系索引、来源绑定；仅数据保全 | 不写 live `entities/moment_*`，不注册 MomentRepository，不进入 scheduler/删除队列/业务扫描 |
| 未来 P13 正式 Entity | 由 P13 的已批准迁移器从封存副本验证后创建，独立提交并验收 | 本轮不创建/激活，不因装载封存而执行任务或修复历史状态 |

“原始记录”指来源档案中的条目字节。官方导出已可能将设备路径转换为资源 token，不能声称恢复了导出前未知的原设备 JSON 字节。封存记录 byte-for-byte 保留；用于未来运行的转换副本单独留痕。

原来源档案保留位置、访问权限和是否可随 Desktop 备份迁移需另批。若来源含凭据，当前整体拒绝；未来 C1/C2 也不能把未脱敏原包自动嵌入普通 Desktop 备份，形成间接秘密泄漏。

## 3. 推荐方案：固定版本、独立命名空间、封闭资源集合

推荐在获得批准后研究 root 内单独的保全容器及 sidecar 清单（名称/格式尚待批准），而非扩大现有 Moments Entity。它属于**新的持久化合同和资源所有权**，必须同时改造备份、root switch、恢复事务及未来版本的兼容读取；不能仅新增一个“忽略未知类型”分支。

拟议清单最小字段：封存格式版本、来源 app/version/官方 commit（来源不能证实时写 UNKNOWN）、来源档案 hash/长度、容器 ID、每条记录的原 entry 路径/类型/ID/hash/长度、资源 entry 路径/hash/长度/媒体类别、原资源字符串与精确字段位置到资源对象的映射、关系状态、验证器版本、验证结论、创建事务身份及保留策略。清单不保存聊天/Prompt/凭据值用于诊断。

命名空间采用 `(archive digest, record type, original ID)`；保留原 ID，禁止导入时随机改 ID 或按 ID 覆盖现有 live 记录。重复同包同类型 ID 即拒绝；跨包同 ID 不自动合并，若同时恢复业务数据会造成不明确所有权则整包拒绝并要求显式选定一个来源。

封存资源由封存容器独立持有，只读且不与 live 图片共用可写路径或硬链接。可研究内部内容寻址去重，但必须有封存容器引用计数/托管记录、哈希校验和事务删除；首版推荐独立物理副本，牺牲空间换取较易证明的保全。不能把 live 媒体 GC 的引用集合当成封存所有权。

## 4. 记录、关联和资源准入规则

| 对象/异常 | 拟议验证与处理 |
|---|---|
| Post ID / Task ID | 非空、类型内唯一；JSON 重复 key、entry 重复、大小写路径别名、Windows 保留名/路径逃逸均拒绝；Post ID 与 Task ID 不因同字符串就视为同实体 |
| `characterCardId` / `sessionId` | 建立指向来源 live 实体的关系表；来源已有缺失可能是官方历史删除语义，不补造实体。记录 `historical-unresolved`，必须有固定版本可接受规则；不能证明则整包拒绝 |
| sender | `senderCharacterId` 可空；非空时核对所属卡内角色或明确历史缺失。保留 senderName/avatar 快照，不按名称匹配新角色，不因同名重新绑定 |
| `postId` | null 不补造；非空应指向同来源封存 post。缺失、跨卡/跨会话不一致、多个任务归属歧义应拒绝，除非独立审计证明为受支持官方历史状态并有明确保全规则 |
| 状态/时间/失败信息 | 原样保留，包括 pending/running 和过期 scheduledAt；不得改成 completed、重新排队或触发补偿生成 |
| 三处图片引用 | 独立枚举 senderAvatar、imagePath、GeneratedImageMetadata.imagePath，按字段位置映射到 inventory 条目；同一路径必须一致，同文件多所有者均登记 |
| metadata 与 post 路径不同 | 两份资源均须保全；不能挑一个删除。若正式语义要求一致却不一致，拒绝并记录结构类别，不能自动修正 |
| 空引用 | 保持空/null 与有值的区别；文字帖/失败占位可没有 imagePath |
| 本地资源 token | 必须落在已验证 inventory，长度/SHA/CRC 一致、无重解析点/符号链接/别名逃逸；不能读取档案外绝对路径来补资源 |
| `content:`、`file:`、旧绝对路径 | 应由官方导出物化；残留未映射路径拒绝。原路径字符串仅作为档案证据保存，不作为本机访问能力 |
| http(s) 资源 | 不抓取。仅 URL 字符串保留不能保证未来图片可用；推荐首版对此类依赖整包拒绝。若未来批准“链接保留”模式，必须降级为有限兼容，不称资源无损 |
| 未知字段/未来 enum/schema | 原包完整保留，但不创建“经验证封存副本”或恢复 live 数据。可单独标为未验证保留物；待新版本审计后才能放行 |
| checkpoint/扩展负载 | 原字节保留；须审计固定版本这些字符串/对象是否包含嵌套序列化路径或秘密，不能只看字段名猜测。未完成递归语义闭包审计即拒绝 |
| 缺失/损坏/超限 | 任何必需资源缺失、认证失败、hash 错误、压缩炸弹、空间不足或无法验证完整 inventory 均拒绝整包；不导入能读到的一部分 |

不能用“未知字段不丢弃”代替“未知字段可理解”。保留原始 bytes 是必要条件；资源闭包、引用语义和再导出可验证性也是放行条件。

## 5. 未来再导出：必须先证明，再允许恢复

存在两个不同产品：

1. **取回原档案**：原 byte-for-byte 文件可取回，适合灾难恢复；不包含 Desktop 后续编辑，不能叫当前状态全量导出。
2. **当前 Desktop 全量迁移档案**：包含当前 live 状态和完整封存数据。Android 官方 registry 不认识 Desktop 封存 sidecar，不能把它直接塞进官方 `entities/` 就声称兼容。

推荐拟议的再导出器在隔离输出中将已验证封存原记录放回官方 `moment_posts`/`moment_tasks` 原逻辑位置，资源保留原 token 对应 entry；输出 inventory/manifest 重算，新档案独立保存。原记录、资源 hash 不变；目标 Android 正式 extract 可以随后做自己的目标路径转换。

如果当前 live 数据占用了原封存所需 entry 且字节不同，不覆盖任何一方，拒绝该全量导出。优先约束未来资源命名避开保留 entry。若必须重写封存路径，则只能建立有批准转换合同的派生记录，并保留原始副本及字段级映射；在此之前不能继续“原记录字节不变”的声称。

角色/会话已在 Desktop 删除时，必须证明目标 Android 能接受该历史孤儿及完整媒体。否则只能取回原包，当前状态全量导出仍 BLOCKED。尤其旧 pending task 重新注入 Android 可能在运行时执行：本合同承诺 Desktop 封存与验证不执行任何任务，但不能保证官方未来打开后无调度。官方导入会重置 `momentsAutoStartConfirmed`（O10），这不是足够的永不执行证明。没有验证过的目标暂停/确认机制时，禁止将任务回注到可运行应用，仅保留原档案取回能力。

因此，**如果在接收前不能证明该封存状态的完整资源引用及安全未来再导出路径，则仍整包拒绝**。原包独立保存不能冒充消除了这一门槛。

## 6. 生命周期与事务

| 生命周期 | 拟议合同 |
|---|---|
| Prepare | 先流式认证完整容器、inventory、来源 hash，再验证字段/资源/关系闭包；所有输出在受控暂存，未确认不改 live |
| 明确确认 | 展示“业务数据恢复 + Moments 仅封存、不提供运行功能”；同时显示是否包含历史孤儿、资源数量及容量，不展示正文/秘密 |
| Schedule / restart | 在根锁、排空后台任务、恢复前快照后，将 live 数据与封存清单/资源纳入同一个可恢复事务；恢复须早于 repository 初始化 |
| 中断 | 复制中断不改变 live；应用一部分后中断，live 与封存一起回滚，不能留下 live 新/封存旧状态；旧/新证据保留 |
| 取消/失败 | 只清理本次已证明归属的暂存，原包、已有封存及 journal 不删除；意外外部写入或证据变更停止恢复 |
| 删除角色/会话/图片 | live 删除不级联删除封存 bytes；历史引用状态单独标注，原记录不改写。封存资源不受 live GC、pending_deletions、替换图片影响 |
| root switch | 新目标完整复制并验证 live 与封存，成功后才切换 root 权威；原根保留；旧版本不支持封存时禁止切换/继续写入 |
| 覆盖升级/降级 | 安装保留根还不够；新版须认识封存版本。旧版本启动/备份不能忽略新根，应拒绝写入而不是将其视缓存清理 |
| 备份/恢复 | Desktop 全量备份必须覆盖封存本体、资源清单、所有权和再导出规则；普通备份仍不携带含秘密原包。现有官方 root 白名单/事务需显式扩展或批准容器合同 |
| 显式删除封存 | 另设用户授权的数据销毁合同、引用检查和可恢复保留期；本草案不默认无限保留或自动到期删除 |
| P13 接管 | 版本化读取器验证原 bytes/资源/关系，生成迁移计划；ID 冲突显式处理，事务创建 live Entity 后校验，成功也不自动删除原封存。pending/running task 默认不激活，另需用户批准 |

当前 Desktop journal 仅承诺所选 root 内的数据文件；它并未实现上述封存版本、跨所有权或 P13 激活事务。本草案不复用一个未证明能容纳 sidecar 的现成路径来绕过设计决策。

## 7. 替代方案、代价及推荐顺序

| 方案 | 优点 | 代价/限制 | 建议 |
|---|---|---|---|
| A 当前整包拒绝 + 原档案保留 | 无新 schema/恢复风险，安全边界清楚 | 无 Moments 全应用迁移可用性 | 继续执行 |
| B 原包作为唯一离线附件 | 实现相对简单，可原样取回 | 凭据泄漏风险；无法承诺当前状态再导出，不满足封存闭包/全量互通 | 不作为 D-038 完成方案 |
| C 本文固定版本独立封存 | 可分离保全与 P13 业务，范围可审计 | 新持久化合同、重复磁盘容量、所有权/事务/导出/旧版本保护成本高 | 推荐研究，先证明闭包和回注任务安全，再申请实施 |
| D 直接注册 Moments Entity | 看似沿用官方 schema | 业务扫描、调度、删除器和未来 P13 争用风险；实际引入运行语义 | 不推荐，超出本任务 |
