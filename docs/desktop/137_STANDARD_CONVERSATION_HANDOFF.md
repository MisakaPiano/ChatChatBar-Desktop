# CCB Desktop 项目对话标准引继指南

版本日期：2026-10-18 JST
适用范围：CCB Desktop 的 Project 审查对话接近长度上限，需要转到新 Project 对话继续。
文件性质：Project 对话常规引继的可复用控制指南；具体操作服从用户最新授权、Project Instructions 和当前任务合同。
Git 权威入口：docs/desktop/137_STANDARD_CONVERSATION_HANDOFF.md，先从适用分支的 Source Map 或 02_CHAT_START.md 定位。

## 你每次只需要做三步

1. 在旧 Project 对话发送本文件中的“旧对话收尾指令”，让它生成本轮专用交接 Markdown。
2. 在同一个 CCB Desktop Project 新建对话，附上专用交接文件，发送“新对话接手指令”。
3. 新对话确认检查点和下一步后，日常 Project 审查转到新对话。原开发 Codex 对话继续使用；除非它也需要引继，不要重复创建开发执行者。

无需每次重新开展全项目审计、重跑全部测试或重做历史验收。常规引继的目标是接续已有工作。

## 何时准备引继

不要等到旧对话完全无法回复。对话已经很长、开始反复解释相同背景，或刚完成一个清楚的提交／验收检查点时，就可以准备。

可以在任务进行中引继，但必须写清谁正在执行、哪些内容尚未提交、谁还可以向原开发 Codex 发指令。旧 Project 与新 Project 不同时调度同一项开发，不同时修改同一 feature。

不要求为了引继把当前工程强行做完，也不要求制造一个新的代码提交。已有任务完成后，只追加一份简短增量交接即可。

## 旧对话应交付什么

每次形成一份有日期的专用交接文件，例如 CCB_DESKTOP_PROJECT_HANDOFF_YYYYMMDD.md。它应能让新对话独立接手，不靠“参见旧聊天全部内容”。

| 内容 | 必须写清的事实 |
| --- | --- |
| 检查点 | 日期与时区、fork、活动分支、完整HEAD、最新来源查询时间、正式validated upstream baseline |
| 提交身份 | 生产源码SHA、测试／证据SHA、文档控制SHA分别列示；有需要时注明直接parent |
| 当前任务 | 目标、任务合同、允许修改范围、禁止事项、实际执行者、正在等待什么 |
| 阶段状态 | 代码、测试、Project审查、用户验收、desktop集成、发布分别记录，不能互相替代 |
| 本对话新增决定 | 用户明确批准的事项、范围、来源消息或已提交文档；提案和批准分开 |
| 债务与缺口 | RED、SKIPPED、NOT TESTED、UNKNOWN、BLOCKED、未解决问题及负责人 |
| 下一步 | 新对话先做的一件事、恢复开发的具体条件、尚未授权的后续事项 |
| 证据入口 | 精确commit链接、相关合同与验收文件、原始证据目录；避免仅给会失效的临时路径 |
| 验证范围 | 哪些来自实际查询，哪些沿用旧记录，哪些没有重新验证 |

长期架构／数据安全原则用简短摘要及权威链接承接，不必每次复制全部历史文件。完整的已批准决定保留在Git或可追溯资料中。

### 新决定还没有进入 Git 时

明确写成“用户已批准／尚未登记Git”，附上可取得的原始消息或附件。需要长期登记时提出最小docs-only任务，不自行把建议改成已批准规范。

“原文无法取得”与“决定不存在”是两回事。记录目前能核对的Git登记、批准状态与补证入口；不能猜原话，也不必据此暂停全部开发。

### Codex 还在执行时

交接必须写明：
- 原开发对话的准确名称及可用入口。
- 最新一次已推送SHA，与尚未提交／推送的工作分开。
- 当前允许继续的范围和已下发的停止点。
- 谁接收Codex下一次报告，谁负责下一轮Project复审。

Project不能把GitHub上看不到的本地改动当作不存在，也不能仅凭GitHub HEAD判断真实工作区clean。没有核对本地状态就写“未核对”。

如果开发Codex自己的对话也要引继，另做工程交接，保留实际工作区、branch／HEAD、未提交diff、index、未跟踪文件、进程／锁和测试状态；不自动reset、清理、切分支或重做整个任务。

## 新对话的第一次接手

新对话先只读完成以下有限核对：

1. 确认自己位于同一个CCB Desktop Project，能够读取专用交接文件和相关资料。
2. 查询交接指定的活动branch live HEAD及desktop HEAD；与交接检查点比较。有变化只核对新增提交，不静默更换审查版本。
3. 依据当前Git读取Source Map、formal baseline和CURRENT，再读本任务合同与相关验收记录。涉及具体官方行为时，定向读取对应baseline的Skill及源码。
4. 标明事实差异、访问不到的必要资料，以及是否真正影响下一项工作。
5. 简短确认接手状态：当前检查点、当前任务、下一步、阻塞项。随后继续既有工作，不先发起全局重新审计。

接手保留用户最新直接授权。按 01 / D-046 连续交付多个 phase，旧单 slice 的 NOT AUTHORIZED、STOP 或 Project 前置审计要求不能撤销本轮 Preview 目标所需实现；无关个人文件、官方 upstream 和真实私密内容 GitHub 上传仍不在授权内。

### 有新增提交时

把专用交接文件的HEAD作为固定边界。后续提交单独作为增量核对：
- 仅文档变化，不冒充新的工程测试或功能实现。
- 源码变化，检查与当前任务相关的影响和必要证据。
- 与下一步无关的历史补证，继续登记，不自动升级为全项目开发阻塞。

如果HEAD或工作区变化会让具体实施不安全，先处理该差异；这不要求重新审计所有已验收阶段。

## Sources 与 Git 如何配合

Git是当前工程和已登记决定的主要共同事实源。Project Sources是方便读取的参考副本，须有版本、来源提交或历史标记。

同名Sources可能指向不同日期。仅凭文件名、上传时间或“CURRENT”字样不能确定权威；应核对文件内来源及精确Git提交。

2026-10-18的资料包和G2交接材料都是固定快照。未来引继时需要核实后续变化，不能永久把其中的HEAD、阶段、审计首项工作或baseline值硬编码为当前事实。

每次引继不需要重新上传整个项目：
- 更新或提供本轮专用交接文件。
- 只在共享资料已经遗漏本轮必要决定，或产生实际版本误导时，刷新相关Sources。
- 本地镜像更新、云端Sources上传、Git提交分别报告，不能互相冒充已完成。
- 清理／替换云端旧附件作为单独资料维护操作处理；不要在一般引继中顺手删除历史资料。
- 不把真实Secrets、用户数据或未经处理的私密材料放入可分享交接文件。

如果Sources维护项尚未关闭，当前任务仍可直接使用可访问的精确Git源码与合同；只有错误版本或缺失资料实际影响该任务时，才阻塞相关工作。

## 引继完成的标准

以下事项都清楚，就可以结束本次引继：

- 专用交接文件已保存，用户有可用的文件或已验证的资料入口。
- 新对话已核对检查点及本任务必要来源。
- 已批准、待审、未实施、未验证、已集成等状态没有被混用。
- 当前执行者和下一次报告的接收对话明确，没有重复下发任务。
- 未覆盖项有保留，下一项具体工作及真正阻塞项明确。

引继完成不要求所有历史问题已解决，也不要求新对话再次批准全部既有决定。它不等于新的工程验收、发布许可或全项目体检PASS。

旧对话保留为历史记录，不自动删除或归档。若旧对话之后又收到最后一份有效结果，将该结果作为增量转交新对话，不重新打开全量交接。

## 旧对话收尾指令

把下面这段发送到即将达到长度上限的 Project 对话：

~~~text
这个Project对话准备引继。请按《CCB Desktop 项目对话标准引继指南》生成一份可下载的本轮专用Markdown交接文件，并附可直接复制的新对话开场指令。

先记录本轮固定检查点：活动branch完整HEAD、desktop HEAD、生产源码与测试/证据/文档提交、查询时间及正式validated upstream baseline。能实际查询的只读核对；没有核对的明确注明。

交接当前任务、用户已批准决定、尚未登记Git的决定、实际Codex执行者、状态、原始证据入口、未解决问题和下一步。代码/测试/Project审查/用户验收/集成/发布分别记录，保留RED、SKIPPED、NOT TESTED、UNKNOWN和未授权范围。

这是常规引继，不发起全面审计、不默认重跑有效测试、不新增开发门禁。保留用户已授权的连续实现范围，按 01 / D-046 接续多个 phase，不在单 slice 结束后等待 Project 批准。原开发Codex继续承担已授权任务，不重复创建执行者。若有任务正在运行，写清下一份报告由新旧哪个Project对话接收。

将本轮新增且需要长期保存的决定列为明确的文档维护项；没有Git落点或无法恢复原话的内容如实标记。最后用简短清单告诉我：新对话需要附哪个文件、先做哪一件事、是否存在真正阻塞。
~~~

## 新对话接手指令

在同一个CCB Desktop Project新建对话，附上旧对话生成的专用交接文件，再发送：

~~~text
继续CCB Desktop Project。请先读取所附的本轮专用交接文件，按《CCB Desktop 项目对话标准引继指南》完成有限的只读接手核对。

查询交接指定的活动branch和desktop live HEAD，与固定检查点比较；有后续变化只核对相关增量。按当前Git Source Map、baseline、CURRENT及任务合同核对下一步，不把旧Sources、历史交接或通用启动模板中的旧阶段文字当作当前事实。

先简短确认：已核对检查点、当前任务、执行中的原Codex对话、下一步及真正阻塞项。然后继续原定工作。不要重新做全项目审计，不重复已完成验收，不默认重跑测试或新增文档门禁；不确定项保留并定向补证。

按用户最新授权及 01 / D-046 继续实现、测试、必要 Fork 集成与 Preview 交付；Project 只做阶段性后置审计。baseline/parity 必须有真实验证，已有 Prompt ownership 和真实私密数据不上 GitHub 的边界继续成立。不要同时给同一任务建立第二个开发执行者。

如缺少必要资料，列出确切缺口及其影响；不猜原文，不将所有历史补证一律当开发阻塞。以后本对话承担Project审查和任务规划，旧对话作为历史记录保留。
~~~

## 完全无法从旧对话生成交接时

用最近一次可靠的Git提交、已提交CURRENT／合同、Codex最后一份完整结果和必要附件建立“临时接手记录”。

新对话先恢复可证明的检查点，不把缺失聊天摘要当作新授权。已经明确授权且有足够合同的工作可以按范围继续；缺少批准或数据安全依据的部分单独等待补证。

不以无法取得旧聊天为理由清空数据、回退提交、重建项目，或宣布以前验收全部失效。
