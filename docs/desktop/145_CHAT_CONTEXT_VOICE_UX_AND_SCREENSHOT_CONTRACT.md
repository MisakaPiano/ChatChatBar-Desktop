## 1. 右键上下文菜单与「…」同一入口

右键聊天内容当前片段，或左键点击**所属整条助手回复底部左侧的「…」**，应弹出**同一套**小型图标+文字浮窗。左键点浮窗外任意位置、Escape、操作完成、切会话即关闭；浮窗紧贴锚点、接近窗口边界时调整方向，不破坏选字/复制/滚轮/焦点。

三组功能各自**严格位于一横行，行内不换行**：

| 横行 | 目标 | 操作（顺序固定） |
|---|---|---|
| 第一行 | 当前整条助手回复 | 重新生成、修复格式 |
| 第二行 | 当前被命中的片段 | 复制、编辑、删除、截图、生成语音 |
| 第三行 | 所属整条回复/消息 | 复制、编辑、删除、截图、生成语音 |

**「生成语音」是单个按钮**，不拆成「生成」＋「语音」。重新生成只作用于整条回复，沿用官方 `regenerationTargetAssistantMessageId` eligibility：仅最近合法助手消息或其特定错误重试，其他历史回复禁用；不得根据当前视口最下气泡误判。对 `…` 没有当前片段时不得偷偷指定其他片段，第二行需明确不可用状态或只有当前选择有效时可用。删除/修复/生成均保持真实消息、版本、session、speaker 所有权和确认语义。

## 2. 回复底部工具栏：左右对齐、单行

固定布局：**左侧 `[复制] [重新生成] […] [喇叭]` —— 可伸缩中间间隔 —— 右侧 `[生成图片] [生图要求]`**。用户最终强调喇叭在**左侧操作组最右端**，不是工具栏右端。所有图标同一行不换行；窄窗应使用受控缩放/横向滚动或合并溢出，但不可让生图一组自然挤到左侧。

左侧 `…` 打开上述三行浮窗。左侧最右**喇叭**在所属助手回复尚无有效语音时为默认颜色，点击执行该回复**整条语音生成/补齐**（仍守多角色朗读选择、可能收费辅助模型确认）；存在本条当前版本的有效录音后转为主题色，点击从**该条第一条有效录音**开始播放；部分录音不能谎称已经补齐，也不自动生成缺失片段。

两枚生图图标独立成右侧对齐组。Git 历史上 P7 两图标原有 `Arrangement.End`；2026-10-13 源码 `efe29a5a` 将按钮并入可横滚的左侧 action toolbar、失去独立右对齐，不是本次 S3–S7 实现的新生图代码。用户头像/名称目前外层右对齐但内部 Row 默认从左排，必须修为与 user 气泡同在**右侧**；合成测试数据不是修复理由。

## 3. 语音生成 Deck：对话视口内，固定单行

撤下长期挤在输入框与消息区之间的 `DesktopVoiceProgress` 及消息后方展开式生成状态。改成**聊天区域内部最下缘**的单行小横条，只在正在生成、等待 AI 文本确认、需处理生成反馈时出现；短状态/进度与取消、按需详情/确认小浮窗分开，最大限度少占纵向空间。状态变化不造成横向按钮漂移。

同一行靠右显示：**「角色音色」标签 + 下拉框**（官方 1.4.1 `ChatScreen.kt` 使用 `选择朗读音色` 标题、`角色音色` 字段）；只在 **effective audiobook on** 时常驻显示，判断 `session.audiobookModeEnabled ?: app.audiobookModeEnabled`。有效听书关闭时隐藏整组常驻声线控件；如果明确的非听书生成仍需要旁白或整条音色，则按上游多角色规则**按需**弹出角色选择，绝不可自动选错。

长期显示的「会话设置已保存」「已删除所选录音」等反馈改为可关闭/有明确消失规则的通知；录音替换的真正完成状态必须明确告知，失败/未知写入不得显示成功。不要让 Deck 因错误信息多行增高，复杂错误放详情浮窗。

## 4. 底部居中音频浮窗与暂停续播

播放中在对话区域底部居中悬浮轻量音频控件：音频动态状态、暂停/播放/停止。第一次 Stop **暂停并保留真实音频位置和待播队列**；图标变播放，点击从暂停位置继续；暂停后的第二次 Stop 关闭浮窗与播放 session，下次主动播放再次显示。无音频且未播放/未暂停不显示。界面位置、控件顺序、大小不可随 playing/paused 改变。

现有 Desktop Windows MCI `play ... from 0` 和 `stopAndDrain` 没有位置/暂停恢复能力；**必须新增平台真实 position/pause/resume 合同及 focused/native 证据**，不可用重新从0播放冒充续播。手动播放优先、picker/formal 焦点互斥、消息删除/替换需释放 native 文件句柄，切会话/关闭/root 变更必须安全取消/排水。

## 5. 连续朗读跨 User 发言

当前代码 `DesktopChatVoiceRuntime.play` 仅向 `VoicePlaybackQueuePolicy.sequenceFrom` 提供**当前一条消息**的录音，故不会在手动开始播放后跨 User 发言读取下一条助手录音。成功生成的多批次按 `messageOrder` 自动入队是已具备的独立机制。

新增跨回复播放应在同一会话当前版本/时间线中，从用户选择的语音或「整条喇叭」入口开始，顺序播完当前回复剩余有效音频，再**跳过 User 发言**继续后续助手回复已有的音频；**不播放 User、不自动发起新 TTS、不穿越会话或旧版本**。用户手动 stop/pause/resume 和会话切换需绝对优先，测试 late-click、queue replacement、消息编辑/删除/排序与音频归属。注意：这项超出官方 1.4.1 手动点击仅同条消息播放的现有行为，须标记 Desktop 用户增强，而不是虚构官方 EXACT。
